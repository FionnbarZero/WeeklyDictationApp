## Implemented contract

The lesson/progress coordinators live under `src/application/writingAcquisition/`; the storage adapter is `src/infrastructure/writingProgressStore.ts`. Only the two application coordinators access acquisition persistence directly. UI and browser storage use their typed command interface; the architectural guard explicitly checks these boundaries.

- `lesson.ts` accepts a Grade 2 Tier 1 writing dataset. It retains every target occurrence in teacher order, validates one-to-four Hanzi and every character guide, and pins the dataset, exact word identities, metadata and guide fingerprints. Existing validated supplementary Pinyin/meaning are used when available; missing metadata is left blank. Missing guides block with the named character/word; no word is silently removed.
- `progress.ts` wraps the existing acquisition envelope and engine with a separate versioned teaching position. The existing engine remains authoritative for Familiar DT, introduction, expanded trials, correction, earned DT and assessment. Teacher completion increments only the outer writing revision and its per-target step count, never the acquisition revision or assessments.
- The teacher position comes from the current whole-word target, not the word temporarily shown in a Familiar DT or correction prompt. Each character completes six steps, including final comparison confirmation. The last confirmed step and permission to enter acquisition are represented by the same atomic record. When the engine selects the next genuinely new word, its zero completed steps open the teacher again.
- `StrokeTeacher` accepts target metadata, the saved initial step and an optional durable step callback. Default v4 behavior remains available. Advancing waits for confirmed storage. Failure keeps the finished drawing available for retry; no incomplete step is marked done. Reload restores only supplied reference strokes and repeats the unfinished step without learner ink. Audio/card behavior remains v4, including seven active seconds and no reveal on replay.
- `writingProgressStore.ts` writes and reads back one bounded record under the existing browser Web Lock helper. Exact command identity and expected revision prevent duplicate/stale callbacks. A pending write retains its exact candidate, including engine randomness, so interrupted confirmation can be retried without generating a different transition. Another tab's changed bytes block overwrite. Invalid records remain untouched.
- Existing acquisition answers use `buildAcquisitionCheckpoint` and `applyAcquisitionCheckpoint`, preserving their normal assessment policy. `initialAcquisitionRevision` lets the wrapper validate that every outer revision is exactly one confirmed teaching step or engine transition. Legacy-target test coverage confirms an already-started target finishes under its original rules; the next new target receives teaching. No real legacy record is imported or rewritten by this preview.
- The existing ProblemReporter pauses the activity clock, animations, drawing and audio. Reports remain on the isolated preview origin until the owner explicitly exports/shares them. No report is sent automatically. Exit returns to the preview menu; opening the lesson again reads its confirmed position.
