# Automatic curriculum updates — isolated prototype, October 25, 2026

## Problem and intended behavior

The combined test app repeatedly refreshed its bundled `/curriculum/beta` files. Those files were validated snapshots, but refreshing them could not discover a later teacher edit. The existing approved curriculum service is healthy and already reads the configured Kindergarten Sheets and Grade 2/Grade 5 Slides sources. This prototype connects to that service without deploying backend code or changing teacher documents, authentication, credentials or family records.

Automatic checks run on entry, every five minutes, on browser focus/visibility return and when connectivity returns. Parent controls offer an explicit retry. New words imported early wait for their scheduled start date in the school calendar (America/Los_Angeles, including daylight saving). An explicit earlier practice-week selection stays selected.

An open writing, reading or game activity keeps its original curriculum and temporary response. A pending source/date change applies at the next visible activity-menu boundary. Report pauses also defer activation. Repeated checks with unchanged content do not rebuild the frame. Unfinished reviewed writing resumes at its saved teaching step; a new active lesson begins its own sequence and preserves the earlier checkpoint.

Requests are serialized and canceled/discarded on grade changes. A separate Web-Lock-protected public curriculum cache prevents an older response from another tab replacing a newer source. Rejected/invalid/partial updates never replace validated curriculum. The last validated source can reopen after a lost connection, server outage or rejected update, with an explicit warning. A fresh browser without valid retained material shows retry instead of a bundled substitute. This is not an offline-installed app.

The actual newly posted source includes Kindergarten 大、马 for October 26 and Grade 5 名字、穷、穷苦、家庭、勇敢、喜爱、伟大 for October 13. Eight missing characters' guides are added only to this prototype from the [same pinned hanzi-writer-data revision already used by the app](https://github.com/chanind/hanzi-writer-data/tree/68d10a4b21150cae5e1ebbd223eed289cf32d90c). Original guides are unchanged. Geometry/count validation and provenance are retained; see the existing Arphic license and stroke data notice. This does not claim all possible future imported characters, definitions or sentence-game support are prepackaged.

## Verification and development evidence

Development runs are retained, including failures. The first laptop run passed 4/7: two navigation checks ran before the replacement frame was ready; one synthetic Grade 5 source changed its confirmation row and correctly failed the existing cohort-confirmation rule. It was narrowed to exact persisted writing records rather than relaxing the checkpoint assertion. A subsequent matrix was interrupted after its driver attempted JSON parsing of non-JSON workspace metadata; the metadata parser was corrected. Its incomplete trace remains recorded.

The expanded laptop run passed 11/12. The Kindergarten failure was first suspected to be the known font-loading click race. A font-ready repeat still failed; a direct DOM probe established the actual cause: the new 马 writing target had no required recorded audio. The existing launch guard correctly retained the menu and reported the missing recording. Four current Kindergarten prompts (马、绿色、黄色、吃) were subsequently recorded with the existing Tingting preview voice at 120 wpm, validated as non-silent PCM WAV, and enabled only for this prototype. No voice/rate or readiness rule was bypassed. The failed matrix and probe are retained. Application source review also identified reopening after a rejected source as a gap; it now revalidates and opens the previous cache with a visible rejection warning.

Final build identity, browser counts, publication receipt, protected-site verification, expiry and email receipt are appended after completion. Detailed logs/screenshots/negative runs are retained under the final prototype artifact folder. Automatic browser speech/media controls establish sequencing, not physical-iPad speaker output. Authenticated cloud, offline installation, cross-device saving, native Warmup integration and support for arbitrary future teacher content remain separate roadmap work.

The first full three-layout matrix passed **33/36**; all three failures were the same missing Kindergarten 马 recording, not curriculum replacement or checkpoint loss. The final matrix additionally plays all four new WAVs through the actual Chromium/WebKit media decoder (muted automation); this establishes playable bytes and complete playback, not physical pronunciation/listening acceptance.

The initial hosted matrix passed **37/39**. Its two WebKit native-recording probes used direct hosted URLs instead of the application's already-approved `prepareRecordingSource` Blob transport, reproducing the known Firebase range-response incompatibility. These were probe-path failures, not proof that in-app playback failed. The corrected probe fetches complete bytes, plays a Blob URL through the real media decoder, and revokes it, matching the unchanged application transport. No application republish or claim of physical speaker acceptance follows from this test correction; both runs are retained.
